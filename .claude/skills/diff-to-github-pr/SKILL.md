# Issue + Diff → GitHub PR 作成ルール

## 前提(絶対厳守)

- **必ず実際のdiffを取得してからPR本文を作成する**。diffを見ずに、issueの受け入れ条件だけから「実装されたであろう内容」を推測して書かない。
- diff取得は `git diff <base>...<branch>` または `git show <commit>` を使う。取得できない場合は、ブランチ名・コミットハッシュをユーザーに確認する。
- **git pushはHTTPS経由(gh認証)を使う。SSH方式(`git@github.com:...`)は使わない。**
  Claude Codeの実行環境は、ホストのSSHエージェント(`ssh-agent`)にアクセスできないため、
  SSH方式のリモートURLだとパスフレーズ入力待ちで無限に停止し、タイムアウトする。
  リモートURLが `git@github.com:...` になっている場合は、
  `git remote set-url origin https://github.com/<owner>/<repo>.git` でHTTPS方式に変更してから進める。
  認証は `gh auth setup-git` 済みであることを前提とする。

## タイトルの命名規則

- 実装PR: `feat: <概要> (SI-XXX)` または `(SI-XXX-YYY)`(範囲は対象issueに合わせる)
- UTのみのPR: `test: <概要> (SI-XXX)`
- 実装+UT混在: `feat: <概要>、<UTの概要> (SI-XXX-YYY)`

## タイトルのプレフィックスの付け方

- feat: 機能の追加
- fix: バグ修正のみ
- docs: ドキュメント変更のみ
- style: コードに影響しないスタイルの修正(white-space, formatting, missing semi-colons, etc)
- refactor: バグ修正や機能追加ではないコード変更
- perf: パフォーマンス向上のためのコード修正
- test: テスト追加・修正のみ
- chore: ビルドツールや補助ツール・ライブラリの変更(例: documentation generation)

## レビュー観点の基本方針(最重要)

レビュー観点には、次の2種類を含める。

**1. 要件充足性(What)**
issue/Jiraの受け入れ条件・機能要件を満たしているか。AIがdiffやテストを読んで確認済みでも省略しない。テストコードの存在は「レビュアーが確認する必要がなくなった」ことを意味しない。

**2. 実装の質、特に見てほしい箇所(How)**
今回の変更の中核となるロジックについて、書き方が適切か、既存パターンと一貫しているか。diffの中で「最も丁寧に見てほしい変更点」を1〜2個特定して書く。ユーザーから重点確認ポイントの指定があれば、必ずここに反映する。

### 例(ステータスフィルタ追加の場合)

```
- statusを指定した場合、指定したステータスのエリアのみが取得されること
- statusが未指定の場合、全ステータスのエリアが取得される(絞り込みなし)こと
- code・name・statusを組み合わせて指定した場合、すべての条件がAND条件で正しく絞り込まれること
- `buildWhere()`のstatus条件追加ロジック(既存のcode/nameと同じスプレッド構文のパターン)が、実装として適切か
```

一方、diffを読んで以下に気づいた場合は、レビュー観点に書かず、PR本文を作成する前に必ずユーザーに確認する。

- **明確なバグ・実装ミス**(例: 似た処理の一方だけ修正が漏れている、ロジックの誤り)
- **設計判断が必要な曖昧な挙動**(例: truthy判定による空文字列・0・nullの扱いなど、意図が読み取れない条件分岐)
- **プロジェクトの既存の運用ルール・慣習との食い違い**(例: 「今後のために残す雛形」が更新されずに消えているなど)

確認の仕方は「〜はバグだと思うので直しますか、それともこのまま指摘事項として残しますか」「〜は意図的ですか」のように、ユーザーが判断できる形で聞く。**「要件を満たしているか」という確認そのものを、この理由で省略してはならない。**

## レビュー観点の書き方(文体)

各項目は「〜を確認してください」のような依頼形にせず、確認すべき事実を体言止め・名詞句で簡潔に書く。

- 良い例: 「statusが未指定の場合、全ステータスのエリアが取得される(絞り込みなし)こと」
- 避ける例: 「statusが未指定の場合、絞り込みがないことを確認してください」

指摘すべき点がなければ「特になし。〜のため問題ありません」のように理由を添える。

## 本文テンプレート

```
## 概要
<何を実装/追加したかの要約。1〜3文。>

## やったこと
- <変更内容を箇条書き。ファイル単位・機能単位で簡潔に>
- スコープ外の変更が含まれる場合も、隠さず記載する

### スコープ外の変更(確認済み)

## レビュー観点
<要件充足性の項目 + 実装の質で特に見てほしい箇所。体言止めで書く>

## 補足
<レビュー判断を求めない、状況説明。書くことがなければセクションごと省略する>

## 関連
- Closes #<issue番号>(issueがある場合のみ)
- Jira: <対象サブタスクのURL、複数ある場合はすべて列挙>
- 親ストーリー: <親ストーリーのURL>
- 依存/対象: <関連する他チケットのURLがあれば>
```

## diffレビューのチェックリスト

本文の「やったこと」「レビュー観点」を書く前に、diffを以下の観点で確認する。

### 基本観点(すべてのPRで確認する)

1. **要件充足性**: issue/Jiraの受け入れ条件・機能要件を一つずつ洗い出す(確認済みでも省略しない)。
2. **実装の中核ロジック**: 今回の変更の中で最も重要な部分を特定し、書き方の妥当性を確認する。
3. **正確性・バグ**: ロジックの誤り、オフバイワンエラー、境界値の考慮漏れがないか確認する。見つけたら前述の手順でユーザーに確認する。
4. **エラーハンドリング**: 例外・異常系(null、undefined、想定外の入力)の扱いが適切か確認する。
5. **セキュリティ**: 入力値の検証漏れ、認可チェックの欠落、機密情報の露出がないか確認する。
6. **パフォーマンス**: N+1クエリ、不要なループ、過剰なデータ取得がないか確認する。
7. **可読性・保守性**: 命名の分かりやすさ、責務の分離が適切か確認する。

### プロジェクト固有の観点(過去に見つかったパターン)

8. **一貫性の欠落**: 似た処理が複数箇所にある場合(例: `findMany`と`count`)、一方だけ修正されていないか確認する。
9. **ドキュメント/コメントの整合性**: JSDocやコメントが実際の実装と食い違っていないか確認する。
10. **エッジケースの扱い(truthy判定)**: `&&`による空文字列・0・nullの扱いなど、意図が読み取りにくい条件分岐があれば指摘する。
11. **スコープ外の変更**: issueと無関係な変更が含まれていないか確認する。含まれる場合は「やったこと」に明記する。
12. **既存の運用ルール・慣習との整合性**: 過去にユーザーと確認済みの慣習(雛形テストの維持など)が今回も踏襲されているか確認する。
13. **テストの網羅性**: 実装のテストはあっても、最終的な出力(レスポンスなど)の検証が抜けていないか確認する。

## 受け入れ条件との差分の扱い方

- **このPRが受け入れ条件を満たすことを目的にしている場合**(実装漏れなど)
  → PR作成前にユーザーへ確認する。
- **このPRがそもそも一部のみを目的にしている場合**(部分実装・クリーンアップのみなど)
  → レビュー観点には書かず、「補足」に事実として書く。

## 作成フロー

1. リモートURLの方式を確認する(`git remote -v`)。`git@github.com:`形式であればHTTPS(`https://github.com/...`)に変更する。
2. diffを取得し、チェックリストで確認する。
3. 要件充足性と、実装の質で特に見てほしい箇所をレビュー観点として書き出す。
4. バグ・設計上の疑問・運用ルールとの食い違いが見つかれば、PR本文の作成より前にユーザーへ確認し、回答を待つ。
5. タイトル・本文案をユーザーに提示し、明確な承認を得るまでPR作成には進まない。
6. 承認が得られた場合のみ、`gh pr create` 等でGitHub上にPRを作成する。
7. 作成後、PRのURLをユーザーに共有する。

## ラベル

作成したPRには `claude-managed` ラベルを付与する。
