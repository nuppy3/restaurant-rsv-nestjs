# Jira → GitHub issue 作成ルール

## 前提(絶対厳守)
- **新しくJiraチケットを作成することは絶対にしない**。既存のJiraチケット(ストーリー・サブタスク)を参照するだけ。
- 親ストーリー配下にサブタスクを新規作成することもしない。すでに存在するサブタスクのみを対象とする。

## タイトルの命名規則
- **サブタスク1件のみを対象にする場合**: `[SI-XXX] <概要>` (単一チケット番号)
- **複数サブタスクをまとめて対象にする場合(連番)**: `[SI-XXX-YYY] <概要>` (範囲表記)
- **複数サブタスクだが歯抜けがある場合**: 代表番号1つ(`[SI-XXX]`)+ issue本文で対象を明記する。無理に範囲表記やカンマ列挙で名前に詰め込まない。

### 例
- 単一: `[SI-608] エリア一覧取得API FilterDTOへのページネーション項目追加`
- 複数(連番): `[SI-608-613] ページネーション機能 実装+UT一式`
- 複数(歯抜け): `[SI-608] ページネーション機能の一部実装(608, 610を対象。609は別対応)`

## 受け入れ条件の統合順序
**Query系(一覧取得・フィルタ・検索など、参照系)の場合:**
FilterDTO → Controller → RegionFilter(値オブジェクト) → Query Service → UT(Query Service) → UT(Controller)
実装のみ/UTのみの場合は該当部分だけ使う。

**Create/Update/Delete系(更新系)の場合:**
このパターンは未検証。対象サブタスクの実際のファイルパス(domain/, application/ など)を確認し、
依存関係(どのファイルがどのファイルを呼び出すか)に沿った順序で並べること。
不明な点があれば、確定させる前にユーザーに確認する。

## issueテンプレート
```markdown
[SI-XXX(-YYY)] <概要>

## Jira
- <各対象チケットのURL>
- 親: <親ストーリーのURL>
- 対象/依存: <関連する他チケットのURL があれば>

## やること概要
<全体の概要文>

### SI-XXX: <サブタスク名>
- <スコープ箇条書き>

### SI-YYY: <サブタスク名>
- <スコープ箇条書き>

## 実装メモ
<!-- 作業しながら随時追記 -->

## 受け入れ条件
<各サブタスクの受け入れ条件を統合>

## 分割PRがある場合
<!-- 基本は1PR想定。分割する場合はここに追記 -->
```

## 確認フロー(重要・省略禁止)
issueの作成はGitHub上への書き込み(不可逆な操作)であるため、以下を必ず守ること。

1. Jiraの内容をもとに、issue本文のMarkdown案を**作成するだけ**で、まだGitHub上には作成しない
2. 作成したMarkdown案を、そのままチャット上に提示し、「この内容でよいか」をユーザーに確認する
3. ユーザーから明確な承認(「OK」「これで」「お願いします」など)を得てから、初めて実際にGitHub issueとして作成する

※ Planモードであっても、この確認フローは省略しない。issueの作成はコード変更ではなく外部システムへの書き込みのため、Planモードの「計画提示→承認→実装」とは別に、このスキル固有のルールとして必ず適用する。

## ラベル
作成したissueには `claude-managed` ラベルを付与する。
